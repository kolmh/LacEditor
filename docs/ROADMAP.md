# LacEditor 性能与架构路线图

本路线图记录 LacEditor 后续性能和架构优化方向。这里的内容代表规划，不代表当前版本已经实现。
每一阶段完成后，必须经过 Debug、Release、静态分析和验收脚本验证，再决定是否进入发布流程。

## 总体原则

- 优先保证输入、滚动、切换标签和保存可靠，再追求更激进的架构升级。
- 保留现有 TextKit 1 编辑路径作为稳定基线，不为了追求新 API 直接重写行号、折叠、输入法和固定行高。
- 后台任务必须绑定文档 ID、内容 revision 和 generation；过期或已取消的结果不得回写界面。
- 不引入网络、登录、遥测或第三方字体；文档内容始终留在本机。
- 大文件模式继续作为性能保护边界，优化应优先降低主线程工作和内存峰值。

## 三阶段路线

### 第一阶段：低风险、高收益的性能清理

目标是减少不必要的全文复制和重复刷新，同时补齐当前最容易回归的编辑器行为测试。

**状态：已完成，待用户验收后再决定是否发布。**

1. Markdown 预览去除全文 payload 拼接。当前不要使用 `"\\(darkMode)|\\(markdown)"` 组合完整文本来判断变化，改用 `textRevision` 与主题状态分别比较。
2. Markdown 预览保持同一个 `WKWebView`，缓存其内部 `NSScrollView` 弱引用，避免每次加载完成都递归查找滚动视图。
3. 搜索缓存改为真正的 LRU，按文档、查询和选项组成键，并在命中、写入和淘汰时更新访问顺序。
4. 增加末尾空行点击回归测试，覆盖 `extraLineFragment`、空文档、连续空行、窗口缩放、标签切换和自动换行。
5. 增加首行、行号滚动和高亮范围回归测试，确认窗口尺寸变化、标签切换和预览开关不会产生重影或错位。
6. 清理当前可修复的应用代码警告；Xcode 27 SDK 对 macOS 26 `ToolbarContent` 的可用性提示，以及 Vendor Tree-sitter 的 C 扫描器提示保留并单独记录，不在本阶段大范围修改第三方代码。

#### 第一阶段的实现边界

- 不改变文本存储模型，不迁移 TextKit 2，不改成 `NSDocument`。
- 不改变 Markdown 解析结果、预览布局和用户设置，只改变变化检测与滚动视图复用方式。
- 不改变搜索结果的排序和快捷键，只替换缓存淘汰策略。
- 测试失败时先修复测试暴露的边界问题，再继续下一项；不通过验收不增加版本号。

#### 第一阶段验收标准

- 编辑 Markdown 时不再为变化检测复制整份正文；预览仍能正确响应正文、主题和文档切换。
- 预览刷新后滚动比例基本保持，关闭和重新开启预览不会出现白屏或旧内容。
- 连续执行查找、反向查找和替换时，缓存命中不会返回其他文档或旧 revision 的结果。
- 末尾空行正文区域、行号区域和空文档均可准确放置光标。
- 窗口缩放、标签切换、侧边栏开关和 Markdown 预览开关后，首行行号与正文保持对齐，无重影。
- Debug、Release、Xcode Analyze 和 `./Scripts/run-acceptance.sh` 通过；记录优化前后打开、预览刷新和搜索的基线数据。

### 第二阶段：核心性能路径

目标是让长代码文件的编辑、滚动和窗口缩放只处理可见区域与真正受影响的语法范围。

**状态：进行中，已完成 Tree-sitter 节点范围剪枝、Markdown/查找任务迁移、文档任务取消注册与对应回归测试。**

1. 让 Tree-sitter 遍历按目标 byte range 剪枝，只返回与可见区或脏区相交的节点。
2. 参照 CotEditor 的 `EditedRangeSet` 强化 `DirtyRangeAccumulator`：合并相邻编辑、保存语法状态边界、按语言配置前后文缓冲。
3. 将语法高亮、折叠和大纲计算拆成相互独立的可取消任务，避免一个任务阻塞其他交互。
4. 从 Markdown 预览、搜索和统计开始，逐步将 `OperationQueue` 任务迁移为可取消的 Swift Concurrency `Task`，不一次性重写全部后台流程。
5. 在 20 MB 以上文件中继续限制全文字数统计和预览频率，保证编辑主线程优先级最高。

#### 第二阶段验收重点

- 50 MB 代码文件输入、快速滚动和切换标签保持可操作，旧任务不会持续堆积。
- 增量高亮不会清除脏区以外的颜色，中文、emoji、注释和字符串边界保持正确。
- 折叠、大纲和括号配对高亮不会抢占编辑输入，也不会把旧 revision 写回当前标签。

### 第三阶段：架构演进与原生能力验证

目标是为未来采用 TextKit 2 或更原生的文档生命周期做好可回退准备，而不是立即替换稳定路径。

1. 抽象 `TextRenderingAttributes` 适配层，统一当前行、括号配对、选区行号和语法颜色的临时渲染属性。
2. 保留 TextKit 1 实现作为默认路径，在独立实验分支增加 TextKit 2 实现。
3. 只有在行号、固定行高、自动换行、中文输入法、折叠、拖选、末尾空行点击和滚动遮挡全部通过回归测试后，才评估逐步启用 TextKit 2。
4. 评估将文件生命周期逐步靠近 `NSDocument` 的收益，但不与 TextKit 2 迁移、大文件重构和界面重构放在同一个版本。
5. 拆分 `AppState.swift` 与 `EditorCoordinator.swift` 的职责，优先按文件操作、恢复、搜索、输入、布局和高亮拆成 extension 或独立服务。

## CotEditor 借鉴与明确不做

CotEditor 最值得借鉴的是：长期存在的文档编辑对象、按编辑范围失效的增量解析、可取消的语法任务，以及 TextKit 1/2 之间的渲染属性抽象。

当前不直接照搬以下方案：

- 不立即全面迁移 TextKit 2。LacEditor 的行号、固定行高、输入法、折叠和末尾空行命中已经围绕 TextKit 1 稳定。
- 不立即整体迁移到 `NSDocument`。当前 Finder 打开、恢复、多窗口、标签和外部冲突已经有专用协调逻辑。
- 不删除现有词法扫描和 fallback 高亮。Markdown、JSON、大文件保护模式以及 Tree-sitter 不覆盖的语言仍需要它们。
- 不为了统一而一次性替换所有后台队列；先从边界清晰、可单独验收的任务开始。

## 每阶段交付要求

- 更新 `CHANGELOG.md` 的“未发布”条目和本路线图的实施状态。
- 更新 README 的当前版本与已实现功能，不把规划项目写成已完成能力。
- 记录基线、改动后数据、测试命令和已知限制。
- 发布前确认工作区无误暂存、构建产物与测试残留，不自动提交或推送未经确认的内容。
